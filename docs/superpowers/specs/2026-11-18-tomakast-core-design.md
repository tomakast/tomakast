# tomakast: ядро, плагинный API и два проверочных плагина

Дата: 2026-11-18. Статус: черновик на согласование.

## Зачем

Собственный лаунчер в духе Raycast, «под себя», который одинаково работает на Linux, macOS и Windows. Raycast — только macOS (Windows в бете), закрытый, на JS; существующие открытые аналоги либо заброшены (Loungy — GPUI, только mac, без плагинов; Gauntlet — iced + Deno/React, остановлен), либо на Qt и завязаны на экосистему Raycast (Vicinae).

Это первая спецификация из нескольких. Она покрывает фундамент: ядро, API плагинов и два плагина, которые доказывают, что оба пути загрузки работают. Остальные фичи (диктовка, переводчик, конвертер, клипборд, окна, caffeinate, заметки, синхронизация, менеджер плагинов) — отдельные спецификации поверх зафиксированного API; их можно вести параллельными подсессиями только после того, как API из этого документа стабилизирован.

## Цели

- Кроссплатформенность без Electron/Tauri/webview. **Linux (основная машина — KDE Plasma на Wayland) и macOS — первоклассные платформы**: всё из этой спецификации работает и проверено на обеих. **Windows — второй приоритет, «но тоже важно»** (слова пользователя); трактовка автора: всё из этой спецификации тоже должно работать и быть проверено, допустимо доводить после Linux и macOS. У пользователя есть мак и машина с Windows для ручной проверки.
- Маленькое ядро-платформа: всё, что не «запуск, поиск, рендер, хоткеи, хранилище, плагины», живёт в модулях.
- Сторонние плагины на любом языке, компилируемом в WebAssembly (component model), грузятся без пересборки приложения.
- Ядро предоставляет плагинам набор UI-представлений; плагины описывают UI данными, ядро рисует.
- Поиск — часть ядра: единый индекс, в который элементы поставляют модули/плагины; ранжирование — в ядре.
- На любую команду и приложение можно назначить глобальный хоткей.
- Быстро и экономно: GPU-рендер, ~0% CPU в фоне, мгновенное открытие.
- Аккуратный, современный, минималистичный вид, близкий к нативному на macOS и Windows и приличный на Linux.

## Не цели (в этой спецификации)

- Диктовка, переводчик, конвертер, история клипборда, управление окнами, caffeinate, заметки — отдельные спецификации.
- Синхронизация. Здесь только требование к хранилищу не мешать ей в будущем (см. «Хранилище»).
- Менеджер/магазин плагинов. Здесь — установка копированием папки.
- Совместимость с расширениями Raycast.
- Поиск файлов (был в исходном запросе) — отдельной спецификацией. Требование к ядру уже здесь: индекс и сопоставление должны выдерживать на порядки больше 10k элементов (сотни тысяч путей), либо файлы приходят как динамический источник со своим индексом. Архитектура индекса не должна это исключать.
- Упаковка и дистрибуция: установщики, подпись и нотаризация на macOS, автообновление (решение автора: отдельной спецификацией; здесь достаточно запуска собранного бинарника и регистрации автозапуска).
- GNOME на Wayland как поддерживаемая цель: без layer-shell и с ограничениями порталов. Должно запускаться обычным окном, но полировка не требуется.

## Анти-цели (провал, даже если «работает»)

- Лаунчер открывается с ощутимой задержкой. Слова пользователя: «должно ощущаться, что нажал кнопку и оно мгновенно появилось, как если бы я символ набрал». Ориентир — ~50 мс от хоткея до кадра в «тёплом» состоянии.
- Сторонний плагин может навредить пользователю: читать или слать данные без разрешения, запускать код, обходить подтверждение разрешений.
- Процесс в фоне потребляет CPU или будит GPU.
- Сторонний плагин может подвесить или уронить UI.
- Плагины выглядят разнобойно: у автора плагина нет способа нарисовать «свой» неряшливый UI.
- Типы GPUI протекают в публичный API плагинов (тогда churn GPUI ломает плагины).

## Ограничения и факты, на которые опирается дизайн

- **GPUI нестабилен по API.** Официальный крейт `gpui` на crates.io не обновлялся с 2025-10; экосистема живёт на еженедельных снапшотах `gpui-pre` и `gpui-kit`/`gpui-component` (0.6 → 0.10 за два месяца, каждый минор ломающий). Решение: пиним точные версии (`gpui-kit = "=0.10.0"`, который пинит `gpui-pre =0.3.12`), обновляемся осознанно. Churn изолирован в крейте рендера, плагинам не виден.
- **Wayland.** Глобальные хоткеи, оверлей, фокус активного приложения и т. п. на Wayland делаются по-разному в разных композиторах. Для KDE: `zwlr_layer_shell_v1` (поддерживается KWin, проверено спайком), портал `org.freedesktop.portal.GlobalShortcuts` (на машине пользователя присутствует, проверено через `busctl`), запасной путь — CLI-тумблер, который пользователь вешает на хоткей в настройках DE.
- **Результаты спайка** (одноразовый прототип на KDE Wayland, GPUI через gpui-kit 0.10, layer-shell overlay, 10 321 элемент):
  - старт процесса и загрузка элементов — 18 мс, RSS 26 МБ; в фоне без окна — 0 тиков CPU за 10 с;
  - **холодное** первое открытие окна в свежем процессе — ~175–210 мс до первого `render`, RSS растёт до ~185 МБ (инициализация GPU-контекста) и после закрытия не возвращается;
  - **повторные** открытия в том же процессе (окно закрывается и создаётся заново) — ~15 мс до первого `render` (3 замера: 15,5 / 15,4 / 15,4 мс). Замер — до вызова `render`, не до показанного кадра; точный «хоткей → кадр на экране» ещё нужно измерить;
  - по умолчанию GPUI на Linux завершает процесс при закрытии последнего окна → нужен `cx.set_quit_mode(QuitMode::Explicit)`;
  - фильтрация 10k строк и прокрутка — пользователь оценил отзывчивость как нормальную;
  - скругления есть, но за окном видна непрозрачная белая подложка. Причина не установлена (кандидаты: заливка корня в gpui-kit/gpui-component, обработка прозрачности в Wayland-бэкенде, отсутствие blur-региона); разобраться в начале работы.
  - Вывод: пересоздание окна само по себе укладывается в бюджет; дорогая только первая инициализация GPU. Значит, нужен «прогрев» при старте демона (инициализировать рендерер заранее), а держать окно живым и прятать — лишь одно из средств, если замер «хоткей → кадр» не уложится. Требование — бюджет, а не конкретный механизм.
- **Prior art по API плагинов:** Zed держит WIT-интерфейс расширений версионированным (`wit/since_v0.x.y/`), хост генерирует биндинги для каждой поддерживаемой версии через `wasmtime::component::bindgen!` и читает версию API из custom section в `.wasm`. Берём ту же схему.
- **Цена «любого языка».** Rust/C/Zig/Go-плагины компактны (сотни КБ) и быстро стартуют; JS/Python через componentize-js/componentize-py тащат интерпретатор (мегабайты, медленнее старт). Это допустимо; первоклассный SDK — Rust.

## Подходы, которые рассматривались

**Модель UI для плагинов**
- **А. Фиксированный набор представлений (как в Raycast) — выбрано.** Плагин отдаёт данные (список, сетка, детали, форма, панель действий, плюс «богатые» компоненты ядра), ядро рисует. Единообразный вид, маленький протокол, легко версионировать. Минус: нестандартный UI требует нового компонента в ядре.
- Б. Дерево примитивов (stack/text/input/image) с диффами. Гибче, но большой и трудно замораживаемый протокол, разнобой во внешнем виде. Отклонено ради аккуратности и стабильности API.

**Рантайм плагинов**
- **WASM component model на wasmtime, в процессе — выбрано** (пользователя привлекает «любой язык»). Песочница, лимиты (epoch interruption, память), трап плагина не роняет хост.
- Встроенный JS (Deno/QuickJS) — только один язык, тяжелее. Отклонено.
- Отдельные процессы по IPC (как pop-launcher) — изоляция сильнее, но дороже по памяти и сложнее. Отклонено для v1: при модели угроз «потенциально вредоносные плагины» достаточно песочницы WASM — у плагина нет никаких WASI-возможностей, только хост-функции ядра с проверкой разрешений, лимиты памяти и времени. Запасной вариант, если песочница окажется недостаточной (например, найдутся уязвимости wasmtime): запуск wasmtime в отдельном процессе-хосте с тем же WIT.
- Нативные Rust-модули (`cdylib`) — нестабильный ABI Rust, без песочницы. Не используется для сторонних плагинов.

**Тулкит**
- **GPUI + gpui-component (через gpui-kit), версии запинены — выбрано.** Лучший вид, Zed работает на всех трёх ОС, есть layer-shell, спайк на KDE подтвердил.
- Slint: стабильный semver 1.x, стили Fluent/Cupertino, но лицензия GPLv3 или royalty-free с условиями, и поддержка layer-shell не подтверждена. Запасной вариант.
- iced: менее отполированный вид; Gauntlet на нём заглох.

## Архитектура

### Два пути загрузки, один внутренний API

- **Встроенные модули** — Rust-крейты, вкомпилированные в бинарник, реализуют внутренний трейт модуля. Имеют доступ к платформенным API (нужны для приложений, позже — диктовки, клипборда, окон).
- **Сторонние плагины** — WASM-компоненты. Хост оборачивает каждый плагин в адаптер, реализующий тот же внутренний трейт. Доступ к системе — только через импортируемые хост-функции и только с разрешениями из манифеста.
- Для ядра оба вида неразличимы: поставляют элементы индекса, команды и представления.

### Крейты (workspace)

Предложение раскладки (детали — на усмотрение исполнителя):

- `tomakast-app` — бинарник: запуск, single-instance, CLI (`tomakast toggle`, `tomakast run <command-id>`).
- `tomakast-core` — реестр модулей, индекс и ранжирование, команды, хоткеи (абстрактно), настройки, хранилище. Без зависимостей от GPUI.
- `tomakast-ui` — рендер представлений в GPUI, окно лаунчера, тема. Единственное место, где живёт GPUI.
- `tomakast-platform` — платформенные шимы: глобальные хоткеи, оверлей-окно/показ-скрытие, автозапуск, открытие файлов/URL, single-instance IPC.
- `tomakast-plugin-host` — wasmtime, загрузка компонентов, версионированные биндинги, лимиты, разрешения.
- `tomakast-plugin-api` — WIT-файлы (`wit/since_v0.1.0/…`) и Rust guest-SDK для авторов плагинов.
- `modules/apps` — встроенный модуль поиска приложений.
- `plugins/calc` — WASM-плагин калькулятора (собирается отдельно в `wasm32-wasip2`, в репо как пример и тест).

### Процессная модель и потоки

- Один процесс-демон. Запускается при логине (автозапуск — платформенный шим), держит окно скрытым.
- Повторный запуск бинарника — клиент: передаёт команду демону через локальный IPC (Unix socket / named pipe) и выходит. Это же — запасной путь хоткеев на Wayland.
- UI-поток никогда не ждёт плагин. Вызовы в плагины идут асинхронно (wasmtime async + background executor GPUI), результаты применяются к UI по готовности. Устаревшие ответы (на старый запрос) отбрасываются.
- Каждый плагин — свой `Store`; лимиты: epoch-дедлайн на вызов (порядка 100 мс для `search`, больше для `run`), лимит памяти. Трап или превышение → плагин помечается сломанным, ошибка показывается в UI, ядро продолжает работать.

### Окно лаунчера

- Окно может пересоздаваться при каждом показе или жить постоянно и прятаться — выбирает исполнитель по замерам; критерий — бюджет открытия (см. «Бюджеты»). GPU-рендерер инициализируется («прогревается») при старте демона, чтобы и первое открытие после логина было быстрым.
- Linux/Wayland: layer-shell, слой Overlay, `KeyboardInteractivity::Exclusive` пока видно.
- Linux/X11, macOS, Windows: безрамочное окно поверх всех, на macOS — non-activating panel (не красть фокус приложения, из которого вызвали), на Windows — tool-window без иконки в таскбаре.
- Прозрачный фон со скруглениями; корень не заливается непрозрачным фоном. Blur/vibrancy — где платформа даёт (macOS vibrancy, Windows Mica/Acrylic, KDE blur), иначе полупрозрачный фон. Нет blur — не блокер.
- Скрывается по Esc, по потере фокуса и после выполнения команды (если команда не открыла представление).
- Тема: светлая/тёмная по системной, акцентный цвет по системе где доступно.

### Поиск и ранжирование (ядро)

- **Индекс** — в памяти, элементы поставляют модули/плагины двумя способами:
  - *статические источники* — модуль публикует набор элементов (приложения, команды плагинов) и обновляет его по событиям (`upsert`/`remove`);
  - *динамические источники* — плагин отвечает на запрос `search(query)` (калькулятор, позже — конвертер, файлы). Вызываются параллельно, с дедлайном; опоздавшие не блокируют выдачу.
- **Элемент индекса**: стабильный id (`<provider-id>/<item-id>`), заголовок, подзаголовок, ключевые слова/алиасы, иконка, тип, список действий (первое — по Enter).
- **Сопоставление**: нечёткое по заголовку/ключевым словам/алиасам (fuzzy с бонусами за начало слова и подряд идущие символы). Цель: ≤ 5 мс на 10k элементов на нажатие.
- **Ранжирование** = релевантность совпадения × вес использования. Вес использования — комбинация трёх сигналов, как просил пользователь:
  - «всегда» — частотность с затуханием (frecency);
  - «сегодня» — частота за текущие сутки;
  - «время суток» — частота в текущем часовом окне (например, ±1–2 часа) по истории.
  Плюс привязка «запрос → выбранный элемент» (если по «fi» обычно открывают Firefox — он первый). Конкретные формулы и коэффициенты — на усмотрение исполнителя; должны быть в одном месте и покрыты тестами.
- **Пустой запрос**: показывает предложения по тем же весам (что обычно запускают в это время).
- **История использования** пишется в хранилище при каждом выполнении действия.

### Команды и хоткеи

- **Команда** — именованное действие модуля/плагина с id `<plugin-id>/<command-id>`, видна в поиске, может открывать представление или выполняться «без UI».
- Глобальный хоткей можно назначить любой команде и любому элементу индекса (приложению) — хранится в настройках как `хоткей → id`.
- Реализация по платформам: Windows — `RegisterHotKey`; macOS — Carbon `RegisterEventHotKey` (или эквивалент); Linux/X11 — XGrabKey; Linux/Wayland — портал GlobalShortcuts, если доступен, иначе пользователь вешает `tomakast run <id>` на хоткей DE (в UI показать подсказку).
- Локальные хоткеи внутри окна: Enter — основное действие, Cmd/Ctrl+K — панель действий, Esc — назад/закрыть, Cmd/Ctrl+1…9 — быстрые действия (по желанию исполнителя).

### Представления (UI-протокол)

Ядро рисует только эти представления; плагин присылает их как данные:

- `list` — элементы с иконкой, заголовком, подзаголовком, аксессуарами (теги/текст справа), секциями; опционально панель деталей справа (markdown). Поле поиска сверху: фильтрация ядром либо пересылка запроса в плагин (`on-query`).
- `grid` — плитки (картинка + подпись), для эмодзи/цветов/изображений.
- `detail` — markdown-контент + метаданные.
- `form` — поля: текст, многострочный текст, чекбокс, выпадающий список, дата; сабмит → событие в плагин.
- `action-panel` — список действий к текущему элементу (Cmd/Ctrl+K).
- `scratchpad` — «богатый» компонент: многострочный редактор, справа от каждой строки — аннотация, которую считает плагин (нужен калькулятору, пригодится конвертеру).
- Плюс тосты/уведомления (`toast`: успех/ошибка/прогресс).

Навигация — стек представлений (push/pop), Esc — pop. Плагин обновляет представление, присылая его новую версию целиком (для v1 достаточно; диффы — оптимизация позже, если понадобится).

Набор представлений расширяется только новыми версиями API.

**Что фиксируется перед параллельной работой** (решение автора): только публичный WIT `0.1.0` и формат манифеста. Внутренний трейт встроенных модулей не замораживается — модули живут в том же репозитории и правятся вместе с ним. Но трейт сразу допускает: долгоживущие фоновые сервисы модуля, собственные окна/оверлеи модуля (индикатор диктовки, редактор заметок), собственные GPUI-компоненты встроенного модуля помимо фиксированного набора представлений.

### Плагинный API (WIT)

Пакет `tomakast:plugin@0.1.0`. Набросок (точные сигнатуры — на усмотрение исполнителя, но структура такая):

- **Модель исполнения** (решение автора): плагин — набор коротких обработчиков, которые вызывает только хост; каждый вызов укладывается в epoch-дедлайн. Долгая или фоновая работа делается так: плагин из обработчика заказывает у хоста асинхронную операцию (таймер, HTTP-запрос), хост выполняет её сам и, когда она готова, вызывает обработчик плагина `on-event` с результатом. Плагину не нужна поддержка async в его языке, поэтому модель работает для любого языка с component model. Асинхронные экспорты component model (WASI 0.3) в wasmtime 50.x есть, но в 0.1 не используются: поддержка у guest-языков пока неравномерна. Это можно добавить в будущей версии API.
- **Экспорты плагина**:
  - `init(ctx)` — однократно при загрузке;
  - `search(query) -> list<item>` — только если плагин объявил себя динамическим источником;
  - `run(command-id, args) -> outcome` — `outcome` = закрыть окно / показать тост / открыть представление;
  - `on-event(event) -> list<effect>` — единая точка для событий: события представлений (ввод в поиск, выбор действия, сабмит формы, изменение текста scratchpad), сработавший таймер, завершившийся HTTP-запрос, изменение преференсов. `effect` — обновить представление, показать тост, upsert/remove в индексе и т. п.
- **Импорты (хост-возможности)**, каждая требует разрешения в манифесте:
  - `index` — upsert/remove своих статических элементов;
  - `storage` — key-value в собственном пространстве имён плагина;
  - `preferences` — чтение настроек плагина (объявленных в манифесте);
  - `clipboard` — запись (чтение — отдельным разрешением);
  - `open` — открыть URL/путь;
  - `http` — асинхронный запрос через хост (`fetch(request) -> request-id`, результат приходит в `on-event`), с allowlist доменов из манифеста. Обычный `wasi:http` плагину не выдаётся;
  - `timers` — `schedule(delay | interval) -> timer-id`, `cancel`; срабатывание приходит в `on-event`;
  - `log`, `toast`;
- Обновления «без запроса пользователя» (асинхронная загрузка данных, прогресс, периодическая переиндексация) делаются эффектами, которые плагин возвращает из `on-event` в ответ на таймер или HTTP. Отдельный push-канал не нужен. Ядро может выгрузить неактивный плагин и загрузить его снова; таймеры плагина при этом переживают выгрузку. Решение автора: это закрывает потребности следующих спецификаций без ломки API 0.1.
- **Версионирование**: как в Zed — WIT лежит в `wit/since_v0.1.0/`; ломающее изменение → новая папка версии; хост держит биндинги для всех поддерживаемых версий и выбирает по версии из custom section в `.wasm`.

### Манифест и установка плагина

- Папка плагина: `<data-dir>/plugins/<plugin-id>/` с `plugin.toml` и `plugin.wasm` (`data-dir` — платформенный, через `directories`).
- `plugin.toml`: id, имя, версия, версия API, автор, список команд (id, заголовок, иконка, режим: view/no-view), объявленные преференсы, разрешения (с allowlist доменов для http).
- Установка в v1 — копированием папки; ядро замечает новые/изменённые папки (file watcher) и перезагружает плагин без перезапуска приложения. Перед первым запуском показывает запрошенные разрешения и спрашивает подтверждение; решение сохраняется.
- Скомпилированные модули кэшируются (wasmtime precompiled), чтобы не тратить время на компиляцию при каждом старте.

### Модель угроз и безопасность плагинов

Сторонние плагины считаются **потенциально вредоносными**, а не просто кривыми.

- Плагин не получает ничего, кроме объявленных в манифесте и одобренных пользователем возможностей. WASI-доступ к файловой системе, переменным окружения, сокетам — не выдаётся вовсе (только через хост-функции ядра).
- Решение по разрешениям привязано к **хешу `plugin.wasm` + `plugin.toml`**, а не только к id. Изменился плагин и **расширился** набор разрешений — повторный запрос подтверждения; разрешения не изменились — без запроса, но смена хеша фиксируется.
- `open`: URL только со схемами `http`/`https`/`mailto` (расширяемо allowlist-ом ядра); пути — только к файлам/папкам, не к исполняемым (на Windows — не `.exe/.bat/.cmd/.ps1/.lnk/.msi` и т. п., на macOS — не `.app`/исполняемые, на Linux — не исполняемые файлы и не `.desktop`). Запуск приложений — привилегия встроенных модулей.
- `http`: только домены из allowlist манифеста, проверка после редиректов; лимиты на размер ответа и число параллельных запросов.
- Квоты: размер `storage` на плагин, число элементов в `index`, частота push-обновлений UI, память и время выполнения (epoch) на вызов.
- `clipboard` чтение — отдельное разрешение, с явной формулировкой в запросе.
- UI-строки от плагина — только данные (markdown рендерится без HTML, без автозагрузки внешних картинок, если нет `http`-разрешения на домен), чтобы нельзя было подделать системные диалоги ядра; источник каждого элемента виден (иконка/название плагина).
- Хост-функции валидируют все входные данные (размеры, количество, кодировки); ошибка плагина не роняет ядро.
- Встроенные модули — доверенные (это код приложения); граница доверия — только WASM.

### Хранилище и настройки

- SQLite (один файл в `data-dir`): история использования, привязки запрос→элемент, KV плагинов, решения по разрешениям.
- Настройки пользователя (хоткеи, тема, включённые модули, преференсы плагинов) — TOML-файл в `config-dir`, редактируемый руками; UI настроек — позже, отдельной спецификацией.
- **Задел под синхронизацию** (сама синхронизация — не здесь): у всех записей стабильные id и метки времени изменения, данные разделены по пространствам имён (ядро / каждый плагин), чтобы потом можно было синхронизировать по частям. Конкретный механизм синхронизации не выбирается.

## Два проверочных плагина

### `apps` — встроенный модуль поиска приложений

Проверяет путь «нативный модуль + статический источник + ранжирование».

- Linux: `.desktop` из XDG data dirs (`/usr/share/applications`, `~/.local/share/applications`, flatpak/snap экспорты), учёт `NoDisplay`, `Hidden`, `OnlyShowIn`, локализованного `Name[ru]`, иконок по теме. Запуск — по `Exec` (через `gio launch`-подобную логику или собственный парсер полей `%f/%u`).
- macOS: `/Applications`, `~/Applications`, `/System/Applications` (бандлы `.app`), имя и иконка из бандла. Запуск — `NSWorkspace`/`open`.
- Windows: ярлыки Start Menu (общий и пользовательский), UWP-приложения — желательно, но не обязательно в v1. Запуск — `ShellExecute`.
- Обновление индекса при изменении каталогов (watcher).
- Действия: открыть (Enter), показать в файловом менеджере, скопировать путь.

### `calc` — WASM-плагин калькулятора-scratchpad

Проверяет путь «сторонний WASM-плагин + динамический источник + богатое представление + хранилище». Пишется на Rust с guest-SDK, собирается в `wasm32-wasip2`.

- В общем поиске: запрос, похожий на выражение (`2+2*3`, `15% of 80`), даёт элемент с результатом; Enter копирует результат.
- Команда «Calculator»: открывает `scratchpad` — многострочный редактор в духе Numi: каждая строка — выражение, справа результат; переменные (`x = 5`, далее `x * 2`), ссылка на предыдущий результат, проценты, базовые единицы (длина, масса, время) — набор единиц на усмотрение исполнителя.
- Не теряет расчёты: содержимое сохраняется в `storage` плагина при изменении и восстанавливается при открытии; история прошлых листов — список с возможностью открыть старый.
- Валюты, позже, — через `http` (в этой спецификации не обязательно).

## Бюджеты производительности (критерии приёмки)

- Тёплое открытие окна (хоткей → первый кадр): ориентир ~50 мс на каждой платформе; главный критерий — субъективно «мгновенно, как набор символа». Замерять автоматически (метка времени получения хоткея → presented frame) и держать в логах/отладочной строке.
  - Порядок действий (решение автора; пользователь сказал «стремиться примерно к 50 мс», про запасной план не решал): (1) план начинается с ограниченного по времени эксперимента на Linux и macOS (и коротко на Windows), до основной UI-работы. Проверить: замер «хоткей → показанный кадр» в тёплом и первом-после-старта состоянии; прогрев рендерера; прозрачность и скругления без подложки; на macOS — non-activating panel, который не крадёт фокус у текущего приложения; на Windows — tool-window без иконки в таскбаре; глобальный хоткей на каждой ОС. Ни один из пунктов macOS/Windows ещё не запускался; (2) если штатно нельзя — поддерживать свой патч/форк платформенного бэкенда GPUI; (3) если и так не выходит — показать пользователю замеры и обсудить; смену тулкита рассматривать только после этого. Поэтому граница `tomakast-ui` должна быть узкой: ядро не знает о GPUI.
- Нажатие клавиши → обновлённая выдача на 10k статических элементов: ≤ 16 мс (динамические источники могут дорисоваться позже).
- В фоне со скрытым окном: ~0% CPU, нет перерисовок.
- RSS со скрытым окном: ориентир ≤ 200 МБ (спайк показал ~185 МБ после первого показа из-за GPU-контекста; снижение — не блокер, но измерять и не ухудшать).
- Зависший плагин не влияет на отзывчивость UI.

## Решено пользователем

- Кроссплатформа Linux/macOS/Windows, без web-обвязок, GPU-рендер.
- Поиск — часть ядра; источники — модули/плагины.
- Плагины может писать кто угодно, грузятся без пересборки; менеджер плагинов — позже, отдельным модулем.
- Плагины на WASM (любой язык).
- UI-модель А (фиксированные представления).
- Тулкит GPUI.
- Первая спецификация: ядро + API плагинов + `apps` + `calc` (предложено, не оспорено).
- Linux и macOS — первоклассные платформы, Windows — второй приоритет, «но тоже важно»; мак и Windows для проверки есть.
- Открытие окна должно ощущаться мгновенным, ориентир ~50 мс.
- Плагины считаются потенциально вредоносными.

## Решения автора спецификации (можно оспорить)

- Windows в этой спецификации: всё должно работать и быть проверено, но допускается доводить после Linux и macOS (так понято «вторым приоритетом, но тоже важно»).
- Модель исполнения плагинов: короткие обработчики + асинхронные операции хоста + `on-event`; без async-экспортов в 0.1.
- Фиксируется только WIT 0.1 и манифест; внутренний трейт модулей эволюционирует.
- Порядок действий при невыполнении бюджета открытия (эксперимент → форк бэкенда → обсуждение → смена тулкита).
- Упаковка и подпись — вне этой спецификации.

- Встроенные модули — Rust в бинарнике; сторонние — WASM; общий внутренний трейт.
- wasmtime в процессе, без отдельных процессов для плагинов.
- Обновление представлений целиком, без диффов, в v1.
- SQLite для данных, TOML для настроек.
- На Wayland — портал GlobalShortcuts + CLI-фолбэк.
- GNOME/Wayland — не целевая платформа в v1.
- Установка плагинов копированием папки, hot-reload по file watcher.
