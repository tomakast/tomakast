# tomakast: plan roadmap for the first spec

Spec: `docs/superpowers/specs/2026-11-18-tomakast-core-design.md`.

The spec covers several subsystems, so it is split into sequential plans. Each plan produces working, testable software on its own.

| # | Plan | Outcome | Depends on |
|---|------|---------|------------|
| 1 | `2026-11-18-plan-1-foundation-linux.md`: core, launcher window and app search on Linux | A daemon on KDE/Wayland: a hotkey opens the launcher, which finds and launches apps and ranks them by usage. Plus a portable window-experiment binary for macOS and Windows | — |
| 2a | macOS: window (non-activating panel), hotkeys, `apps` for `.app` bundles, autostart | Plan 1 functionality on macOS, verified on the user's Mac | 1 |
| 2b-1 | `2026-11-18-plan-2b1-views.md`: views, navigation, action panel, dynamic sources (native modules), WASM tracer bullet, WIT 0.1 draft | Modules open list/grid/detail/form/scratchpad views on a stack, Ctrl/Cmd+K action panel, toasts; module calls off the UI thread; `apps` reveal/copy-path; demo module | 1 |
| 2b-2 | Plugin host: wasmtime, WIT 0.1 bindings and imports, manifest, permissions (hash-bound), quotas, hot reload, precompile cache, kitchen-sink test plugin, `calc` | A third-party WASM plugin loads from a folder without rebuilding; calculator scratchpad; the spec's threat model. WIT 0.1 frozen at the end | 2b-1 |
| 3 | Windows: window (tool window), `RegisterHotKey`, `apps` for the Start Menu, autostart | Same on Windows, verified on the user's machine | 1, 2a |

Plans 2a and 2b-1 can run in parallel, but both edit `crates/ui`: 2a owns `crates/ui/src/window.rs` (window kinds per OS), while 2b-1 must keep its `window.rs` changes to update plumbing and put views under `crates/ui/src/views/`. Merge one before the other's UI tasks start, or rebase carefully. 2b-2 touches `plugin-host`, `plugin-api` and `plugins/calc` and does not conflict with 2a. Linux and macOS are both first-class platforms, and macOS must not lag behind Linux.

The spec requires a window experiment on Linux and macOS before the main UI work. Plan 1 therefore has a task that builds a portable experiment binary. The user runs it on the Mac and on Windows right after the skeleton is in place, before plans 2a and 3. If the Mac results are bad, the plan order is revisited.

Once plan 2b-2 is done, WIT 0.1 and the manifest format are frozen. From then on, the follow-up specs (dictation, clipboard, window management, converter, translator, caffeinate, notes, file search, sync, plugin manager) can run in parallel. Some built-in modules (caffeinate, window management on Linux, dictation, file search) can start earlier, once plan 2b-1 Task 2 lands (it changes the module trait to async workers and adds dynamic sources). Per-feature wishes, open questions and the earliest point each one can start are in `docs/superpowers/backlog.md`.
