# Plan 2b-1: views, navigation, action panel and dynamic sources

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The launcher stops being a single list. Modules can open views (list, grid, detail, form, scratchpad), push and pop them on a navigation stack, show an action panel (Ctrl/Cmd+K) and toasts, and answer queries as dynamic sources. Module calls never run on the UI thread. `apps` gains "show in file manager" and "copy path". The plan also measures WASM cost with a tracer bullet and drafts WIT 0.1, so plan 2b-2 (WASM host + `calc`) can map 1:1 onto core types.

**Architecture:**
- **Core view model.** `tomakast-core` gains a GPUI-free view model (`view.rs`, `effect.rs`). It is flat, because WIT has no recursive types, and it mirrors the WIT draft.
- **Module workers.** Every module runs on its own worker thread (`ModuleHost`). The core sends it requests and receives replies as `CoreEvent`s, tagged with request ids and query generations so stale replies are dropped.
- **UI.** `tomakast-ui` gets a `ViewStack` with one renderer per view kind. The root search list is the first view on the stack.

**Tech Stack:** as in plan 1. New: wasmtime 50 (`component-model`, sync API) and wit-bindgen 0.63, for Task 1 only. The `wasm32-wasip2` target joins `rust-toolchain.toml`.

**Spec:** `docs/superpowers/specs/2026-11-18-tomakast-core-design.md`, sections "Views (UI protocol)", "Plugin API (WIT)", "Process model and threads", "Threat model". Roadmap: `docs/superpowers/plans/2026-11-18-roadmap.md`. Plan 1 follow-ups: `docs/superpowers/plans/2026-11-18-plan-1-followups.md`.

## Global Constraints

- All of plan 1's Global Constraints still apply (`docs/superpowers/plans/2026-11-18-plan-1-foundation-linux.md`), among them:
  - GPUI pinned `gpui-kit = "=0.10.0"`, used only in `tomakast-ui` (and the daemon until the follow-up M3 facade);
  - core is free of GPUI and platform code;
  - performance budgets;
  - **agents never run a keyboard-grabbing window on the user's session** (`TOMAKAST_NO_KEYBOARD=1`, headless tests);
  - **all dev runs use `TOMAKAST_HOME=<tmp>`**;
  - per-user IPC socket;
  - docs and code comments in English.
- **The UI thread never waits on a module.** No module method is called from the UI thread after this plan's Task 2.
- **Stale replies are dropped.** Each search carries a `generation: u64`. Each action and view event carries a `RequestId`. A reply with an old generation, or for a popped view, is ignored.
- **The core owns typed text.** Every text-bearing event (query, form field, scratchpad text) carries a `revision: u64` that the UI increments on each edit. A module reply that updates the same view applies only its non-text parts (rows, annotations) and only if its `revision` equals the view's current revision. The text itself is set only when a view is pushed.
- **Views are flat.** No view contains another view; sections are a field on rows, not nesting. Every type in `view.rs` / `effect.rs` must be expressible in WIT 0.1 (Task 3 checks this).
- **Untrusted text is data.** Markdown is rendered without HTML and without loading remote images. Item ids coming from modules are validated: they must contain `/`, contain no newline or control character, and be at most 256 bytes. Invalid ids are dropped with `warn!`.
- Dynamic source deadline: **100 ms** per query per module. Late results for the current generation are still merged when they arrive. Results for an older generation are dropped.
- `plugins/*` and `experiments/*` crates are **not** workspace members. `cargo test --workspace` must not need `wasm32-wasip2`.

## Review Focus

1. **Typing fast while a module answers slowly.** Typed text is never overwritten or reordered, and results always belong to the latest query. Test: Task 2 `stale_generation_results_are_dropped`; Task 4 `late_reply_does_not_clobber_query`.
2. **A module panics or hangs inside `run_action` / `search` / `on_view_event`.** The UI stays responsive, other modules keep working, and the failing call surfaces as an error toast. Test: Task 2 `panicking_module_does_not_kill_core`, `hung_module_search_misses_deadline`.
3. **Esc on a pushed view.** Esc pops one level; Esc on the root hides the window. Showing the window again starts at the root with an empty query. Test: Task 4 `escape_pops_then_hides`.
4. **An action panel on an item with one action, and on a view without a selection.** Ctrl+K does nothing harmful (no panel, or a panel with only the primary action). Enter in the panel runs the chosen action. Test: Task 5 `action_panel_runs_secondary_action`, `action_panel_without_selection_is_noop`.
5. **Scratchpad with long lines, empty lines and many lines.** Annotations stay on the line they belong to. No wrapping: long lines scroll horizontally. Test: Task 8 `annotations_align_with_lines`.

**Interfaces:**
- Produces (core):
  - `#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)] pub struct RequestId(pub u64)`.
  - `pub trait Module: Send + 'static`. It is called only on the module's own worker thread:
    - `fn id(&self) -> &'static str`
    - `fn start(&mut self, ctx: ModuleContext)`
    - `fn run_action(&mut self, item: &Item, action_id: &str) -> anyhow::Result<Vec<Effect>>`
    - `fn is_dynamic_source(&self) -> bool { false }`
    - `fn search(&mut self, query: &str) -> anyhow::Result<Vec<Item>> { Ok(vec![]) }`
    - `fn on_view_event(&mut self, view: &ViewId, event: ViewEvent) -> anyhow::Result<Vec<Effect>> { Ok(vec![]) }`

    `Effect`, `ViewId` and `ViewEvent` are defined in Task 3. Task 2 lands minimal placeholders in `effect.rs` that Task 3 expands: `Effect::{CloseWindow}` and an empty `ViewEvent`.
  - `CoreEvent` gains:
    - `ActionFinished { request: RequestId, item: ItemId, query: String, result: Result<Vec<Effect>, String> }`
    - `SearchResults { provider: String, generation: u64, items: Vec<Item> }`
    - `ViewEventFinished { request: RequestId, view: ViewId, result: Result<Vec<Effect>, String> }`
  - `Core` methods:
    - `request_action(&mut self, item: &ItemId, action_id: &str, query: &str) -> anyhow::Result<RequestId>` — it returns at once; the action runs on the worker;
    - `search(&mut self, query: &str, now: LocalNow) -> SearchSnapshot` — static hits are synchronous; dynamic sources are asked with a new generation;
    - `apply(&mut self, ev: CoreEvent, now: LocalNow) -> CoreUpdate`;
    - `send_view_event(&mut self, provider: &str, view: &ViewId, event: ViewEvent) -> anyhow::Result<RequestId>`.
  - `pub struct SearchSnapshot { pub generation: u64, pub hits: Vec<Hit> }`. The hits merge static hits and current-generation dynamic results.
  - `pub enum CoreUpdate { None, ItemsChanged, Results(SearchSnapshot), ActionDone { request: RequestId, effects: Vec<Effect> }, ActionFailed { request: RequestId, message: String }, ViewEffects { request: RequestId, view: ViewId, effects: Vec<Effect> }, ViewFailed { request: RequestId, view: ViewId, message: String } }`.
  - Usage is recorded on `ActionFinished` with `Ok`. The record uses the query and the `now` of that `apply` call.
  - Ranking of dynamic items: `combined_score(DYNAMIC_MATCH_SCORE, usage)` with `pub const DYNAMIC_MATCH_SCORE: u32 = 1_000`, so answers (calc, converter) sort above static matches.
  - `ItemId::is_valid(&self) -> bool` implements the validation rule from Global Constraints. `ModuleContext::replace_items` and `SearchResults` handling drop invalid ids with `warn!`.
- Worker rules:
  - each module gets one thread, named `module-<id>`, fed by an unbounded command channel;
  - a panic inside a module call is caught with `catch_unwind` and reported as `Err("module <id> panicked")`; the worker keeps serving;
  - `search` is skipped when a newer search generation is already queued for that module (coalescing).
- `FakeModule` gains configurable `search` results, a delay, and panic-on-call switches.
- UI and daemon:
  - `LauncherView` uses `request_action`, and handles `ActionDone` / `ActionFailed` from `CoreUpdate` (hide on `CloseWindow`, error line on failure);
  - `daemon.rs` forwards `core.events()` → `core.apply(ev, LocalNow::now())` → `LauncherController::core_update(update, cx)`. This replaces `core_changed`;
  - `Request::Run` uses `request_action`.

The riskiest UI piece, so it is mandated no-wrap.

**Files:**
- Create: `crates/ui/src/views/scratchpad.rs`

**Interfaces:**
- Produces a multiline editor (gpui-component `TextareaState` in no-wrap mode). Next to each line, a right-aligned annotation column is rendered at the same line height and vertical offset: muted color for results, the theme's danger color for `is_error`.
